我們的 Loop / Graph 是怎麼設計的？

資訊如何從 5 篇混亂的原始食譜（raw/）被取得、標準化檢查、編譯進 16 頁 wiki/，再經過「大綱確認 → 逐頁腳本審核 → HTML 渲染」三階段圖譜產生成教學簡報？本專頁完整呈現架構圖、實際檢查紀錄與 Shift-Left 反思。

步驟三：說明你的 Loop / Graph 設計

一、雙迴圈＋三階段簡報生成圖譜 (End-to-End Staged Graph with 4 Verification Gates)

我們將整個系統拆解為兩大部份：前半部是 「Loop A：Wiki 知識擷取與編譯迴圈（處理 5 篇 Raw 資料）」，後半部是 「Graph B：三階段教學簡報生成圖譜（先大綱 → 後逐頁內容 → 最終 HTML 投影片）」，並在每個階段設置強制檢查節點（Gate 0 ~ Gate 3）與退回修正迴圈（Feedback Loops）：

🔁 1. 哪些步驟會重複執行？

  • Loop A（Ingest 編譯迴圈）：每丟入一篇新文獻就完整重複執行一次（共執行 5 輪）。且每輪不是只寫 1 頁，而是網狀更新 7~8 個既有 Wiki 頁面，讓跨品項比較（如瑪德蓮 vs 可麗露）持續累積深化。
  • Gate 退回迴圈：在 Gate 0、Gate 1、Gate 2、Gate 3 只要檢查未通過，就會觸發虛線箭頭退回上一節點重新換算或重新生成。

🛡️ 2. 哪些地方需要檢查或重新生成？

  • Gate 0（寫入 Wiki 前）：檢查食譜單位（顆/杯→克）與百分比分母基準（總粉=100% vs 總重=100%）。
  • Gate 1（大綱階段）：檢查學習曲線（必須先教烘焙百分比，後面才能放流派百分比表）並與使用者確認架構。
  • Gate 2（逐頁腳本階段）：檢查數據與 Wiki 是否 100% 一致、每個法文/化學術語是否都有「初學者白話比喻」、單頁字數是否會導致投影片太擠。
  • Gate 3（HTML 階段）：檢查 RWD 版面、Tabs 切換與隨堂測驗互動功能。

💡 3. 為什麼這樣設計？

  • 關注點分離（Separation of Concerns）：將「數據清洗（Gate 0）」、「教學架構（Gate 1）」、「內容正確性與白話轉譯（Gate 2）」與「前端 HTML/CSS 排版（Gate 3）」徹底拆開。
  • 當最後一步要生成 HTML 投影片時，文字與數據早已在 Stage 2 驗證完畢並鎖定，AI 只需專注把版面與互動做好，完全不會發生一邊寫 HTML 一邊算錯烘焙百分比或漏寫白話解釋的問題！

步驟四：進行反思 (Reflection)

三、實作反思：哪個節點最常出錯？如何把檢查往前移（Shift-Left）？

❓ 1. 哪一個節點最常出錯？

在實際執行過程中，有兩個節點最容易出錯：

  • 資料層最常出錯的節點 —「跨來源食譜的單位換算與百分比基準對齊」：不同原始食譜混用「顆、杯、小匙」與「公克」，或是混淆「焦化前生奶油重（含 16% 水分）vs 焦化後淨重」，以及「有粉蛋糕 vs 無粉內餡（除以零）」的分母衝突。
  • 簡報生成層最常出錯的節點 —「直接從 Wiki 一步跳到 HTML 程式碼生成」：如果沒有先拆出「大綱確認」與「逐頁內容腳本檢查」，直接讓 AI 生成 HTML 投影片，AI 會同時忙著寫 CSS/JS 又忙著塞資料，極易發生「單頁塞入過多大表格導致畫面破版」、「專有名詞忘了寫初學者白話比喻」，或是「發現大綱方向不對時，必須整份幾千行 HTML 打掉重寫」的嚴重返工。

⏪ 2. 你發現問題後，把檢查往前移到了哪一個步驟？（Shift-Left Validation）

我們實施了雙重「檢查前移（Shift-Left）」：

  • 第一次前移（從「做簡報時」前移到「Ingest 寫入 Wiki 之前」的 Gate 0）：規定任何原始食譜在寫入 wiki/recipes/ 之前，必須先在 Gate 0 完成公制克數換算、蒸發水分補償與烘焙百分比驗算。確保寫入 Wiki 的每一張表格都是 100% 可直接並排比較的乾淨數據。
  • 第二次前移（從「HTML 渲染後」前移到「Stage 1 大綱確認 Gate 1」與「Stage 2 逐頁純文字腳本審核 Gate 2」）：在動手寫任何一行 HTML 之前，先在 Gate 1 確認 8 頁大綱與學習順序，接著在 Gate 2 對純文字的「逐頁內容腳本」進行數據一致性核對、初學者白話比喻檢查，以及單頁容量預判（提前決定哪裡要用 Tabs 收納）。

🔧 3. 你有沒有因此修改 workflow / graph？為什麼？

有的！我們因此將原本單純的線性流程，修改為上方看到的「Dual-Loop + 三階段 Staged Graph（含 Gate 0 ~ Gate 3 四道檢查閘門）」：

  • 為什麼要這樣修改？ 因為在沒有拆分階段與前移檢查前，「資料錯誤」、「教學順序錯誤」與「HTML 排版錯誤」會全部糾纏在最後一個節點爆發（除錯成本最高）。
  • 修改 Graph 之後，每個節點各司其職：Gate 0 保證 Wiki 數據零矛盾 → Gate 1 保證簡報大綱符合初學者認知動線 → Gate 2 保證逐頁文字有白話比喻且單頁容量適中 → Gate 3 只需專心把 HTML 視覺與互動做好。這不僅讓最終產出的教學簡報品質大幅提升，每次修改也只需要退回對應的小階段，真正發揮了 Agent Graph 工作流的工程價值！
